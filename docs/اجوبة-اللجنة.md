# دليل أجوبة لجنة الدفاع — مشروع newRopey

نظام إدارة الكلية التقنية الهندسية زوارة — Flask + SQLite + JavaScript، واجهة عربية RTL.

> **طريقة استخدام هذا الدليل:** كل سؤال أجابته مع **مرجع `file:line`** حقيقي من الكود. إذا طلبت منك اللجنة "أرني هذه الصلاحية في الكود" فأنت تدلهم على الملف والسطر مباشرة. في نهاية الدليل يوجد ملحق «اعرف كودك» يلخص أهم المواقع.

## 0) نظرة عامة (لأول دقيقتين من الدفاع)

- **ما النظام؟** تطبيق ويب لإدارة كلية: المستخدمون والأدوار، الأقسام، أعضاء هيئة التدريس، المقررات، الجداول الدراسية، الامتحانات، محتوى المقررات، الحضور، المراسلات، سجل التدقيق.
- **التقنيات:** Python 3 + Flask 3 (Application Factory + Blueprints)، SQLite (مع WAL و Foreign Keys مفعّلة)، Jinja2 للقوالب، Bootstrap + Tailwind للواجهة، JavaScript للمكونات التفاعلية، Werkzeug لكلمات المرور، Waitress للسيرفر في الإنتاج.
- **الأدوار (7):** `research_development`، `faculty_affairs`، `head_of_department`، `teacher`، `exam`، `dean` (العميد — مراجعة قراءة فقط)، `visitor` (الزائر العام).
- **نموذج الصلاحيات:** `Role → Permissions → Navigation` — الدور يعطي مجموعة صلاحيات (نصوص)، والقائمة الجانبية تُبنى من الصلاحيات.

**البنية المعمارية (طبقات):**

```
المتصفح (HTML/JS)
   │
   ▼  HTTP Request
Flask Route (routes/*.py — Blueprint)
   │  decorators: @login_required @permission_required @csrf_required
   ▼  Business Logic
Service (services/*.py)
   ▼  Data Access
Repository (database/repositories/*.py)
   ▼  SQL
SQLite (database/data.db)  ← schema.sql + schema.py (migrations)
   │
   ▼  jinja render_template / JSON (api/helpers.py: ok/err)
قالب HTML أو JSON → المتصفح
```

مصدر هذه الخريطة: `README.md` + `app.py:92` (create_app) + `routes/` (24 Blueprint).

## المدرس الأول: Python / Flask

### 1) لماذا اخترت Flask لبناء مشروعك؟
لأنه **إطار خفيف ومرن** يسمح لي ببناء المشروع من الصفر بدون تعقيد، ولأنه مكتوب بلغة Python ويوفر:
- ربط سهل بـ SQLite (`flask_db.py`).
- نظام **Blueprints** لتقسيم المشروع (`routes/`).
- **Application Factory** (`app.py:92`) لتهيئة التطبيق بشكل نظيف.
- نظام Decorators لحماية الصفحات (`security/authorization.py`).
- مقارنة: Django كامل ومتكامل لكنه يفرض هيكل وأداة ORM جاهزة؛ أنا أردت السيطرة الكاملة على الاستعلامات والهيكل.

### 2) ما هي Python، وما دورها في مشروعك؟
Python هي **لغة البرمجة** التي كُتب بها المشروع كاملاً (السيرفر). دورها: معالجة الطلبات، التحقق من البيانات، تنفيذ SQL على قاعدة البيانات، بناء صفحات HTML عبر Jinja2، وإرجاع JSON للواجهة.

### 3) ما الفرق بين Python وFlask؟
- **Python** = اللغة (تحوي وصلات، وقوائم، ودوال، وغيرها).
- **Flask** = إطار عمل (Framework) مكتوب بلغة Python، يبسط بناء تطبيقات الويب: التوجيه للروابط، التعامل مع الطلبات/الجلسات، وتوليد الردود.
- تشبيه: Python كالإنجليزية، وFlask كالصيغة الرسمية للرسالة الرسمية.

### 4) ما المقصود بـ Backend في مشروعك؟
الجزء الذي يعمل **على السيرفر** ولا يراه المستخدم: كل ما في `routes/` و`services/` و`database/` و`security/`. هو المسؤول عن المصادقة، الصلاحيات، حفظ وجلب البيانات، وتجهيز البيانات للواجهة. الواجهة (Frontend) فقط تعرض النتيجة.

### 5) ما هو الـ Route في Flask؟
**رابط URL يربط بدالة (View Function).** مثال `routes/auth.py:49`:

```python
@bp.route('/login', methods=['GET', 'POST'])
@csrf_required
def login():
```

عندما يزور المستخدم `/login` يستدعي Flask دالة `login()`.

### 6) ماذا يحدث عندما يطلب المستخدم URL معيناً؟
1. المتصفح يرسل **HTTP Request** (GET/POST) إلى السيرفر.
2. `before_request` في `app.py:174` يفحص الصلاحيات، و`app.py:216` يفحص CSRF.
3. Flask يطابق المسار مع جدول الـ Routes ويستدعي الدالة المناسبة.
4. الدالة تنفذ منطقها (مصادقة، استعلام، تحقق).
5. تُرجع استجابة: صفحة HTML (render_template) أو JSON (jsonify) أو Redirect.

### 7) ما الفرق بين GET وPOST في Flask؟
- **GET:** جلب بيانات، تُمرر في الـ URL (`request.args`)، آمن لإعادة التحميل، يظهر في التاريخ.
- **POST:** إرسال/تغيير بيانات، تُمرر في جسم الطلب (`request.form` أو JSON)، يُستخدم مع النماذج وكل عملية تعديل.
- في المشروع: `GET` لعرض الصفحات، `POST` للحفظ والحذف والرفع. مثال معرفة نوع الطلب: `routes/auth.py:53` (`if request.method == 'POST':`).

### 8) ما هو الـ View Function؟
**دالة Python مرتبطة برابط معيّن** عبر `@app.route` أو `@bp.route`، مهمتها: استقبال الطلب، تنفيذ المنطق، ثم إرجاع الرد. مثال: `login()` في `routes/auth.py:51`، `dashboard()` في `routes/dashboard.py:47`.

### 9) ما وظيفة render_template()؟
تحويل قالب **Jinja2** (HTML) إلى صفحة HTML نهائية مع تمرير بيانات إليها:

```python
return render_template(template, user=current_user(), stats=stats, ...)
```
`routes/dashboard.py:103`. السبب: فصل HTML (الشكل) عن Python (المنطق والبيانات).

### 10) ما هي Jinja2؟
**محرك قوالب (Template Engine) الخاص بـ Flask.** يسمح بكتابة HTML فيها أكواد مثل `{{ variable }}` للطباعة و`{% if %}` و`{% for %}` للمنطق البسيط. مثال `templates/shared/layouts/base.html:39` (`{% for item in nav_items %}`).

### 11) كيف ترسل البيانات من Flask إلى HTML؟
1. بتمريرها كوسيط في `render_template('x.html', key=value)`.
2. في القالب تُقرأ بـ `{{ key }}` أو `{% for %}`.
3. فئة `@app.context_processor` (مثل `inject_navigation` في `app.py:122` و`security/authorization.py:262`) تضيف دوالاً/بيانات **متاحة في كل الصفحات** دون تمريرها يدوياً (مثل `csrf_token()`, `nav_items`, `has_permission`).

### 12) كيف تستقبل البيانات القادمة من Form؟
عبر كائن `request`:
```python
username = request.form.get('username', '').strip()
password = request.form.get('password', '')
```
`routes/auth.py:55-63`. وإذا كان JSON: `request.get_json()` (مثل `auth/change-password` و`api/helpers.py:55`).

### 13) ما وظيفة request في Flask؟
كائن **Global (متاح أثناء الطلب)** يحتوي كل بيانات الطلب: `request.method`، `request.form` (بيانات النماذج)، `request.args` (معاملات URL)، `request.get_json()` (جسم JSON)، `request.files` (الملفات المرفوعة)، `request.remote_addr` (عنوان IP). مثال: `routes/auth.py:54`.

### 14) ما وظيفة session؟
**تخزين بيانات المستخدم بين الطلبات في كوكيز موقّعة** (مشفرة بمفتاح `SECRET_KEY`). تُستخدم لحفظ حالة تسجيل الدخول. أنا أخزّن فيها: `user_id`, `role`, `roles`, `department_id`, `hod_department_id`, `teacher_id`, `_csrf_token`. إعداداتها في `config.py:53-61` (HttpOnly, Secure, SameSite=Lax).

### 15) كيف استخدمت Sessions في تسجيل الدخول؟
في `services/user_service.py:85-181` (دالة `authenticate`): بعد التحقق من كلمة المرور، أكتب:
- `session['user_id']`, `session['username']`, `session['roles']` (كل أدواره), `session['role']` (أعلى دور = دور الهبوط)، و`session['_csrf_token']`.
- وعند `logout` (`routes/auth.py:104`) أستدعي `session.clear()` لإنهاء كل شيء.

### 16) ما الفرق بين Authentication وAuthorization؟
- **Authentication (المصادقة):** "من أنت؟" — التحقق من الهوية (username + password). مكانه `user_service.authenticate`.
- **Authorization (التخويل):** "ماذا يُسمح لك أن تفعل؟" — التحقق من الصلاحيات. مكانه `security/authorization.py` و`app.py:174`.
- مثال: تسجيل الدخول = مصادقة. منع teacher من صفحة R&D = تخويل.

### 17) كيف يعرف النظام أن المستخدم قام بتسجيل الدخول؟
بفحص `'user_id' in session`. يحدث ذلك في:
- `security/authorization.py:137` داخل `login_required`.
- `security/auth.py:17` داخل `get_user()` (يقرأ database حسب `session['user_id']`).
- `app.py:182` في `before_request`.

### 18) كيف يعرف النظام دور المستخدم؟
من `session['role']` (الدور النشط) و `session['roles']` (كل الأدوار)، والتي تُكتب عند تسجيل الدخول في `user_service.py:136-140`. وهناك **نموذج الأدوار المتعددة**: جدول `user_roles` يخزن كل أدوار الشخص (`schema.sql:42`).

### 19) كيف تمنع مستخدماً من الدخول إلى Route غير مسموحة له؟
بثلاث طبقات:
1. **Decorator على الدالة:** `@permission_required('courses.manage')` (`security/authorization.py:147`).
2. **طبقة عامة قبل كل طلب:** `enforce_permissions` في `app.py:174` (Deny-by-default — مسار بدون صلاحية مُعلنة يُرفض).
3. **واجهة غير قابلة للقرصنة:** إخفاء الأزرار وحده غير كافٍ؛ الحماية الحقيقية في السيرفر.

### 20) ما هو الـ Decorator الذي استخدمته لحماية بعض الصفحات؟
أربعة أنواع في `security/authorization.py`:
- `@login_required` (:133) — يتطلب تسجيل الدخول.
- `@permission_required('perm')` (:147) — يتطلب صلاحية معينة (أي دور يمنحها).
- `@role_required('teacher')` (:177) — يتطلب دوراً محدداً.
- `@any_role_required(...)` (:203) — قبول أي دور من القائمة.
- بالإضافة إلى `@csrf_required` في `security/csrf.py:93`.

### 21) ما الفرق بين Role وPermission؟
- **Role (دور):** هوية المستخدم مثل "teacher" أو "head_of_department".
- **Permission (صلاحية):** عملية محددة مثل `courses.manage`, `timetable.edit`, `exams.manage`.
- العلاقة: **كل دور يمتلك مجموعة صلاحيات** عبر `ROLE_PERMISSIONS` في `core/constants/permissions.py:16`.

### 22) لماذا استخدمت نظام صلاحيات بدلاً من الاعتماد على اسم الدور فقط؟
لأن نموذج الأدوار المتعددة يجعل المستخدم يمتلك عدة أدوار. وإذا تحققت من "الدور فقط" فهذا يعني: لا يمكن للمستخدم أن يكون teacher ورئيس قسم في آن واحد، وأي دور جديد يتطلب تعديل كل الشروط. أما بالصلاحيات:
```python
roles = get_granted_roles()          # قائمة كل أدواره
if not has_permission(roles, required_perm, dept_id):  # اتحاد الصلاحيات
    return redirect(...)
```
`security/authorization.py:161-166`. وهذا يجعل إضافة دور جديد مجرد إضافة سطر في قاموس الصلاحيات.

### 23) ما هو Blueprint في Flask؟
**وحدة تنظيمية للـ Routes** — مجموعة روابط لها `url_prefix` ويمكن تسجيلها في التطبيق. مثال `routes/courses.py` يبدأ بـ `bp = Blueprint('courses', __name__, url_prefix='/courses')`. جميع Routes المقررات تبدأ بـ `/courses`.

### 24) لماذا قسمت المشروع إلى Blueprints؟
للفصل والمحافظة: كل نطاق عمل له ملفه (`auth.py`, `teachers.py`, `courses.py`, `timetable.py`, `exams.py`, `hod_pages.py`, `teacher_pages.py` ...). هذا يسهل: إضافة ميزة دون كسر غيرها، وتتبع الأخطاء، وقراءة الكود. تسجيلها يتم في `app.py:66-88` و`app.py:222-244`.

### 25) ما المقصود بـ Application Factory؟
**دالة تنشئ التطبيق** بدل إنشائه مرة واحدة على مستوى الملف:

```python
def create_app():
    app = Flask(__name__)
    ...
    return app
```
`app.py:92`. أي أن إنشاء التطبيق مؤجل إلى لحظة استدعاء الدالة.

### 26) لماذا استخدمت Application Factory؟
للأسباب التالية:
- **سهولة الاختبار:** أنشئ تطبيقاً جديداً مع قاعدة بيانات مختلفة لكل اختبار (`tests/conftest.py`).
- **إعادة الاستخدام:** `app.py`، `serve.py:43`، `wsgi.py` كلها تستدعي `create_app()`.
- **تهيئة مرنة حسب البيئة** (تطوير/إنتاج) عبر `Config`.

### 27) كيف يتم إنشاء تطبيق Flask في مشروعك؟
1. `create_app()` في `app.py:92` يقرأ الإعدادات من `Config` (`config.py:41`).
2. `db_init_app(app)` يهيئ قاعدة البيانات (`flask_db.py:14,157`).
3. تسجيل Blueprints و `register_api(app)` (`app.py:222-244`).
4. إضافة error handlers (404, 413, 429, 500) و security headers (`app.py:257-335`).
5. التشغيل: `python app.py` (تطوير) أو `python serve.py` (إنتاج بـ Waitress) — `serve.py:57`.

### 28) كيف يتصل Flask بقاعدة البيانات؟
عبر `flask_db.py`:
- `get_db()` (flask_db.py:47) يفتح اتصال SQLite **لكل طلب** ويخزنه في كائن `g` (context من Flask).
- `close_db()` (flask_db.py:66) يُغلق الاتصال في نهاية الطلب عبر `@app.teardown_appcontext` (`app.py:105`).
- الاتصال نفسه يُهيأ في `database/connection.py:18` (تشغيل Foreign Keys، وضع WAL).

### 29) أين تتم معالجة البيانات قبل إرسالها إلى قاعدة البيانات؟
في **طبقة الخدمات (services)** — وهي طبقة الـ Business Logic. مثال `services/user_service.py` للتحقق من كلمة المرور وقواعد الأدوار، و`services/course_content_service.py` لآلة الحالة. الـ Routes تستدعي الخدمات بدل كتابة SQL مباشرة في معظم الحالات.

### 30) كيف تتعامل مع الأخطاء في Flask؟
- معالجات أخطاء للشبكة: 404, 413, 429, 500 في `app.py:257-297`.
- أخطاء العمل مرفوعة كـ `AppError` في `core/exceptions.py` ويُلقطها `handle_app_error` (`app.py:260`) — إذا الطلب AJAX يرجع JSON وإلا flash + redirect.
- تسجيل الأخطاء في ملف `logs/ropey.log` عبر `_setup_logging` (`app.py:29`).

### 31) ماذا يحدث إذا أرسل المستخدم Form ناقصاً؟
البيانات المطلوبة تعود فارغة (`.get()` ترجع None أو القيمة الافتراضية)، ونفحصها يدوياً:
```python
username = request.form.get('username', '').strip()
if not username or not password:
    return render_template(..., form_error='اسم المستخدم أو كلمة المرور غير صحيحة', ...)
```
`routes/auth.py:55-97`. أو في API: `if not username or not password: return err('...', 422)` في `api/auth.py:62`.

### 32) كيف تتحقق من صحة البيانات قبل حفظها؟
تحقق يدوي (Validation):
- `validate_password` في `security/__init__.py` (قوة كلمة المرور) — مستخدم في `routes/auth.py:170`.
- التحقق من التطابق: `if password != confirm: error = 'كلمة المرور غير متطابقة'` (`routes/auth.py:167`).
- فحوصات منطقية في الخدمات مثل `course_content_service._validate_step` (منع submit إذا مجموع الأسابيع أكبر من 12).
- فحوصات التكرار: `_validate_code_updates` في `routes/courses.py` (مثال: منع كود مقرر مكرر).

### 33) ماذا يحدث من لحظة ضغط المستخدم على زر حفظ حتى يتم تخزين البيانات؟
1. المتصفح يرسل **POST** مع حقول الـ form و `_csrf_token`.
2. `before_request` يتحقق من CSRF (`app.py:216`) ثم الصلاحية (`app.py:174`).
3. Flask يوجّه إلى دالة الـ route.
4. الدالة تنفذ `request.form.get(...)` ثم تستدعي **Service**.
5. الـ Service يتحقق، ثم ينفذ **INSERT** عبر `db.execute(...)`.
6. **`db.commit()`** يحفظ فعلياً (بدونها لا تُحفظ البيانات في SQLite).
7. إعادة توجيه (PRG) لمنع إعادة الإرسال عند تحديث الصفحة.

### 34) إذا حذفت @login_required من Route محمية، ماذا يمكن أن يحدث؟
- طبقة الأمان العامة ما زالت في `app.py:174`: بما أن الـ route لا يملك صلاحية معلنة (`_required_permission` غير موجودة)، تُفعل سياسة **Deny-by-default** → يعاد توجيه المستخدم أو يُرفض الطلب.
- لكن **الأفضل لا تعتمد** على هذه فقط؛ لأن `login_required` هي التي تنقل غير المسجل إلى `/login`. بالحذف، قد يُمنح وصول بطرق أخرى في مسارات لا تمر بالمعالجة العامة (مثل API أو routes للعامة). الحذف = ثغرة محتملة.

### 35) إذا حذفت return render_template(...) من View، ماذا سيحدث؟
- بدون أي `return` ترجع الدالة **None**، وFlask يرمي خطأ 500 ("View function did not return a response").
- إذا وضعت `return` لكنك نسيت `render_template` ومررت قاموساً بدلاً منه، ستظهر أخطاء قالب.

### 36) لماذا فصلت الملفات إلى Routes وTemplates وServices وغيرها؟
**للهندسة المعمارية متعددة الطبقات (Separation of Concerns):**
- `routes/` → الاستقبال والتوجيه وإرجاع الرد.
- `services/` → منطق العمل (business logic).
- `database/repositories/` → الوصول للبيانات (SQL).
- `templates/` → العرض (HTML).
- `security/` → الحماية (auth, CSRF, authorization).
- `static/` → JS و CSS.
النجم طريق: يمكن تغيير أي طبقة دون كسر الباقي.

### 37) كيف تساعدك هذه الهيكلة في تطوير المشروع؟
- **الاختبار:** طبقات منفصلة = اختبار أسهل (يوجد 70+ اختبار في `tests/`).
- **الصيانة:** تعديل Query في Repository لا يلمس منطق العمل أو الواجهة.
- **إعادة الاستخدام:** استدعاء نفس الخدمة من Route HTML أو من API.
- **الأمان المركزي:** كل الحماية في `security/` + `before_request` + الـ decorators.

## المدرس الثاني: SQL

### 1) لماذا تحتاج إلى SQL في مشروعك؟
لأن البيانات (مستخدمون، مقررات، جداول، امتحانات) يجب أن **تحفظ وتسترجع بطريقة منظمة**. SQL هي اللغة القياسية للتعامل مع قاعدة البيانات. المشروع يستخدم SQLite ويُنفذ استعلامات SQL مباشرة عبر `sqlite3`.

### 2) ما هي قاعدة البيانات؟
**مستودع منظم للبيانات** يخزنها في جداول مترابطة. في مشروعي `database/data.db` (ملف واحد من SQLite). القاعدة الحالية تحتوي جدولين وأكثر: `users`, `teachers`, `courses`, `timetable`, `exam_schedule` ... إلخ (انظر `schema.sql`).

### 3) ما الفرق بين SQL وقاعدة البيانات؟
- **SQL** = لغة الاستعلام (SELECT, INSERT, UPDATE, DELETE) — هي "الوسيلة".
- **قاعدة البيانات** = مكان تخزين البيانات — هي "المكان".
- مثل: SQL هي اللغة التي تتكلم بها مع ملف القاعدة.

### 4) ما وظيفة SELECT؟
**استرجاع (قراءة) بيانات** من جدول/جداول. أعدّ `SELECT id, name FROM departments WHERE hidden = 0 ORDER BY name` — مثال `services/timetable_service.py:159`.

### 5) أين استخدمت SELECT في مشروعك؟
في كل مكان تقريباً:
- جلب المستخدم مع قسمه: `security/auth.py:20` (`SELECT u.*, d.name AS department_name FROM users u LEFT JOIN departments d ...`).
- جلب جدول الأستاذ: `services/timetable_service.py:958` (SELECT مع عدة JOIN).
- عرض بيانات اللوحة الرئيسية في `services/dashboard_service.py`.

### 6) ما وظيفة INSERT؟
**إضافة سجل جديد** إلى جدول. مثال `services/user_service.py:356`:
```python
INSERT INTO teachers (name, email, phone, academic_number, ...) VALUES (?, ?, ?, ?, ...)
```

### 7) متى تستخدم INSERT في النظام؟
عند **إنشاء** أي كيان: مستخدم جديد، محاضر، مقرر، قاعة، حصة في الجدول، امتحان، تسليم محتوى مقرر (`course_content_submissions`)، رسالة، إشعار.

### 8) ما وظيفة UPDATE؟
**تعديل سجل موجود**. مثال تغيير كلمة المرور:
```python
UPDATE users SET password = ? WHERE id = ?
```
(تستدعيها `user_service.reset_password` → `user_repository.update_password`). وأنت تستخدم أيضاً `UPDATE courses SET code = ? WHERE id = ?` في `routes/courses.py`.

### 9) أين يمكن استخدام UPDATE في مشروعك؟
- تعديل بيانات محاضر/مقرر/قاعة/مستخدم.
- تحديث حالة تسليم محتوى المقرر (`status`) في `course_content_service._apply_transition`.
- تحديث حالة حضور عضو هيئة تدريس (`faculty_attendance`).
- تغيير كلمة المرور.

### 10) ما وظيفة DELETE؟
**حذف سجل/سجلات**. مثال `timetable_service.delete_entry` → `DELETE FROM timetable WHERE id = ?`. والنظام يعتمد أيضاً حذفاً ناعماً (`deleted_at`) في بعض الجداول للمحافظة على سجل التدقيق.

### 11) ما وظيفة WHERE؟
شروط التصفية — تحدد **أي الصفوف** يتأثر بها الاستعلام. مثال: `DELETE FROM timetable WHERE id = ?` مع `id` يحذف حصة واحدة فقط.

### 12) لماذا يعتبر WHERE مهماً؟
لأنه **بدونه يستهدف الاستعلام كل الصفوف**: `UPDATE users SET role='teacher'` بدون WHERE يغيّر دور الجميع! لذلك كل التعديلات والحذف يجب أن تحمل شرطاً (عادة `id = ?`).

### 13) ما وظيفة ORDER BY؟
**ترتيب النتائج** تصاعدياً (افتراضي) أو تنازلياً (`DESC`). مثال ترتيب الأقسام: `... ORDER BY name` في `timetable_service.py:161`.

### 14) كيف يمكن ترتيب المقررات أو الجداول؟
```
ORDER BY c.name        -- أبجدي
ORDER BY c.year, c.semester   -- سنة ثم فصل
ORDER BY t.start_time  -- الجدول الزمني
ORDER BY v.id DESC     -- الأحدث أولاً (مثال إصدارات الجداول timetable_service.py:238)
```
مثال فعلي لجلب المقررات مرتبة: `_build_course_payload` في `timetable_service.py:552` (`ORDER BY c.name`).

### 15) ما هو JOIN؟
**ربط صفوف من جدولين أو أكثر** عبر علاقة مشتركة (عادة Foreign Key). مثال `security/auth.py:20` يربط `users` بـ `departments` لجلب اسم القسم.

### 16) لماذا نحتاج إلى JOIN في مشروع إدارة الكلية؟
لأن البيانات **موزعة على جداول** حسب التصميم، فنحتاج دمجها للعرض:
- عرض حصة الجدول يحتاج اسم المقرر + اسم المحاضر + اسم القاعة + اسم القسم: `services/timetable_service.py:958` يجمع `timetable` مع `courses` و`rooms` و`departments`.
- عرض محاضر يحتاج بياناته من `teachers` واسم قسمه من `departments`.

### 17) ما الفرق بين INNER JOIN وLEFT JOIN بشكل مبسط؟
- **INNER JOIN:** يرجع الصفوف **المتطابقة فقط** في الجدولين. لو محاضر بلا قسم لن يظهر.
- **LEFT JOIN:** يرجع **كل صفوف الجدول الأيسر** حتى لو لم يوجد تطابق (العمود الفارغ يساوي NULL).
- مثال في مشروعك: `security/auth.py:20` يستخدم `LEFT JOIN departments` بحيث يظهر المستخدم حتى لو `department_id = NULL` (كل المستخدمين يظهرون).

### 18) أعطني مثالاً على ربط جدول المستخدمين بجدول آخر.
```sql
SELECT u.*, d.name AS department_name
FROM users u
LEFT JOIN departments d ON u.department_id = d.id
WHERE u.id = ?
```
`security/auth.py:20`. وربط المستخدم بالأستاذ عبر `teachers.user_id` في `user_service.py:146` (`SELECT id, department_id FROM teachers WHERE user_id = ?`).

### 19) ما وظيفة GROUP BY؟
**تجميع الصفوف** حسب عمود ما للحسابات (COUNT, SUM ...). مثالَ: `selectdepartment` يجمع عدد مقررات كل قسم. مثال من الكود: تجميع الإحصائيات في `dashboard_service`، وأيضاً `GROUP BY department_id, semester` في الترحيلات (schema.py:687).

### 20) ما الفرق بين WHERE وGROUP BY؟
- **WHERE:** يُطبَّق **قبل** التجميع — يصفّي الصفوف الخام.
- **GROUP BY:** يُطبَّق **بعد** — يجمّع الصفوف المصفّاة.
- مثال: `WHERE hidden = 0 GROUP BY department_id` — أولاً نهمل المخفي، ثم نحسب لكل قسم.

### 21) ما هو Primary Key؟
**المعرّف الفريد لكل سجل** في الجدول. عادة `id INTEGER PRIMARY KEY AUTOINCREMENT` في كل جداول `schema.sql` (مثل `departments.id` سطر 2). يضمن عدم تكرار وتحديد السجل بشكل فريد.

### 22) ما هو Foreign Key؟
**عمود يشير إلى Primary Key في جدول آخر** — يربط السجلات. مثال `users.department_id REFERENCES departments(id)` في `schema.sql:18`.

### 23) لماذا نستخدم Foreign Key؟
**للحفاظ على تكامل البيانات**: يمنع `teacher` بقسم غير موجود، ويمنع حذف قسم مرتبط به سجلات دون معالجة. ونفعّله في كل اتصال: `PRAGMA foreign_keys = ON` في `database/connection.py:25`.

### 24) ماذا يحدث إذا حاولت إضافة Foreign Key غير موجود؟
يرفض SQLite الإدراج (IntegrityError) لأن القيد `REFERENCES` مكسور. مثال: إدخال `timetable` بـ `course_id = 999` غير موجود في `courses` يفشل. المشروع يصطاد هذه الأخطاء ويعرض رسالة للمستخدم.

### 25) ما المقصود بـ Constraint؟
**قاعدة تُفرَض على البيانات** عند الكتابة: فرادة، عدم الفراغ، صحة المرجع، عمود غير قابل للنفي. أمثلة:
- `NOT NULL` (العمود مطلوب).
- `UNIQUE` (لا تكرار).
- `REFERENCES ... ON DELETE ...` (التكامل المرجعي).

### 26) ما أمثلة الـ Constraints الموجودة في قاعدة البيانات؟
من `schema.sql`:
- `username TEXT NOT NULL UNIQUE` (سطر 14) — لا تكرار ولا فراغ.
- `UNIQUE(course_id, department_id)` في `course_departments` (سطر 276).
- `UNIQUE(user_id, role)` في `user_roles` (سطر 47) — مستخدم + دور لا يتكرران.
- `ON DELETE CASCADE` (مثل `course_content_submissions` → `course_content_curriculum` سطر 458).

### 27) كيف تمنع تكرار بيانات معينة؟
بثلاث طرق:
1. **Constraint في القاعدة:** `UNIQUE` مثل `users.username` (`schema.sql:14`).
2. **فحص قبل الحفظ:** `_validate_code_updates` في `routes/courses.py` يفحص كود المقرر داخل الدفعة والقاعدة.
3. **INSERT ... OR IGNORE / OR REPLACE:** لتفادي كسر الـ UNIQUE (مثل `timetable_service.py:691`).

### 28) كيف تتأكد من أن البيانات المطلوبة لا تكون فارغة؟
- على مستوى القاعدة: `NOT NULL` (`users.username NOT NULL`) وشيكات `CHECK`.
- على مستوى التطبيق: فحص `if not x: return error` في الـ routes (مثل `api/auth.py:62` "اسم المستخدم وكلمة المرور مطلوبان")، و`validate_password` للتحقق من القواعد.

### 29) ما المقصود بـ Transaction؟
**مجموعة عمليات تُنفذ أو تُلغي كلها كوحدة واحدة** — تبدأ بـ `BEGIN`/أو تلقائياً، وتغلق بـ `COMMIT` (نجاح) أو `ROLLBACK` (تراجع كامل).

### 30) لماذا قد نحتاج إلى Transaction؟
عند تعديل **عدة سجلات مرتبطة** يجب أن تنجح كلها معاً أو لا شيء:
- `publish_directly` في `course_content_service.py` تنقل التسليم بسلسلة خطوات (submit → approve → publish) كلها في معاملة واحدة؛ إن فشلت خطوة → `db.rollback()` وكل شيء يتراجع.

### 31) ماذا يحدث إذا فشلت عملية حفظ البيانات في منتصف العملية؟
مع Transaction صحيحة لا يبقى أي شيء نصف مكتوب — نستدعي `rollback()` وتعود القاعدة كما كانت. الكود: `try: ... db.commit() except Exception: db.rollback(); raise` (نمط موجود في `course_content_service.publish_directly`).

### 32) كيف يقوم Flask بتنفيذ استعلام SQL؟
- عبر اتصال SQLite من `get_db()` (`flask_db.py:47`).
- ثم `db.execute('SQL', (params,))` ثم `db.fetchall()/fetchone()` للقراءة، و`db.commit()` للحفظ.
- SQLite يوفر `?` كبدائل (parameterized queries) — يُستخدم عملياً في كل الاستعلامات لمنع **SQL Injection** (لا إلصاق نصي للقيم).

### 33) كيف تنتقل البيانات من SQL إلى Python ثم إلى HTML؟
1. `db.execute(...).fetchall()` → صفوف `sqlite3.Row` (تتصرف كقاموس) — فيها أسماء الأعمدة كخانات.
2. تُمرر كقاموس/قائمة إلى `render_template`.
3. Jinja2 تعرضها في HTML: `{% for course in courses %}<tr>{{ course.name }}</tr>{% endfor %}`.
مثال حي: `routes/dashboard.py:103` يمرر `stats` و`teacher_data` إلى القالب.

### 34) كيف تسترجع بيانات المقررات من قاعدة البيانات؟

## المدرس الثالث: Database Design

### 1) لماذا اخترت استخدام قاعدة بيانات في المشروع؟
لأن النظام يدير **بيانات كثيرة ومترابطة** (مستخدمون، محاضرون، مقررات، جداول) تحتاج تخزيناً دائم ومنظماً، مع استعلام سريع وسلامة البيانات. SQLite اختير لأنه ملف واحد، سهل، بدون تثبيت سيرفر، ويناسب نظام الكلية.

### 2) كيف صممت قاعدة البيانات؟
- المخطط في **`database/schema.sql`** (جدول + قيد + فهرس).
- الترحيلات والتهيئة المؤقتة في **`database/schema.py`** (`ensure_schema` تعمل عند كل تشغيل وتضيف أعمدة/جداول ناقصة عبر `_safe_add_column` — schema.py:51).
- مقسمة حسب النطاقات في `database/domains.py` (Identity, Academic, Scheduling, Examinations, Communication, Auditing).

### 3) ما الجداول الرئيسية الموجودة في النظام؟
`users`، `departments`، `teachers`، `courses`، `rooms`، `timetable`، `exam_schedule`، `course_content_submissions`، `course_content_curriculum`، `teacher_messages`، `teacher_materials`، `faculty_attendance`، `notifications`، `history`، `password_resets`، `user_roles`، `course_departments`، `course_prerequisites` — كلها في `schema.sql`.

### 4) لماذا فصلت البيانات إلى عدة جداول؟
**لتجنب التكرار والتناقض (Normalization)**: كل كيان حقيقي (مستخدم، قسم، مقرر، محاضر) له جدوله، والعلاقات عبر Foreign Keys. لو وضعنا كل شيء في جدول واحد، لجُهّد الكثير وتناقضت البيانات عند التعديل والحذف.

### 5) ما المقصود بـ Primary Key؟
**العمود الذي يعرّف كل سجل بشكل فريد** — `id INTEGER PRIMARY KEY AUTOINCREMENT` في كل جدول. يضمن الوصول السريع والفريد للسجل.

### 6) لماذا لكل جدول Primary Key؟
بدونه لا يمكن تمييز سجلين متشابهين ولا ربط الجداول ببعضها ولا حذف/تعديل سجل واحد بدقة. كل Foreign Key في النظام يشير إلى Primary Key في جدول آخر.

### 7) ما المقصود بـ Foreign Key؟
عمود في جدول يشير إلى **Primary Key في جدول آخر** — هو "جسر" العلاقة. مثال `timetable.course_id REFERENCES courses(id)` (`schema.sql:181`).

### 8) كيف استخدمت Foreign Keys في مشروعك؟
في كل جدول يرتبط بغيره: `users.department_id → departments`، `teachers.user_id → users`، `teachers.department_id → departments`، `timetable.course_id → courses`، `exam_schedule.course_id → courses`، `course_content_curriculum.submission_id → course_content_submissions` ... مع تفعيل `PRAGMA foreign_keys = ON` (`database/connection.py:25`).

### 9) ما العلاقة بين المستخدمين والأدوار؟
**نموذج الأدوار المتعددة**: مستخدم واحد له عدة أدوار عبر جدول ربط `user_roles` (Many-to-Many):
- `users.id` (طرف أول)
- `user_roles` (جدول ربط: `user_id` + `role`) — `schema.sql:42`
- `users.role` (عمود) يبقى **دور الهبوط الافتراضي** فقط.
القراءة: `user_service.py:136` (`find_roles_by_user`).

### 10) ما العلاقة بين الأقسام وأعضاء هيئة التدريس؟
**One-to-Many**: قسم واحد → عدة محاضرين. عبر `teachers.department_id REFERENCES departments(id) ON DELETE SET NULL` (`schema.sql:63`). ويوجد `hod_department_id` لتحديد قسم رئاسة القسم.

### 11) ما العلاقة بين الأقسام والمقررات؟
**Many-to-Many** عبر جدول ربط `course_departments` (course_id + department_id + semester) — `schema.sql:271`. أي مقرر يُدرَّس في عدة أقسام، والقسم عنده عدة مقررات.

### 12) ما العلاقة بين المقرر والمحتوى الدراسي؟
**One-to-Many تقريباً**: مقرر واحد ← عدة تسليمات (`course_content_submissions`) عبر `course_id` (`schema.sql:425`). وكل تسليم له "منهج" (curriculum) بعلاقة One-to-Many عبر `course_content_curriculum.submission_id` (`schema.sql:458`).

### 13) ما العلاقة بين المقرر والجدول الدراسي؟
**One-to-Many**: مقرر واحد يظهر في عدة حصص (`timetable`) عبر `timetable.course_id REFERENCES courses(id) ON DELETE CASCADE` (`schema.sql:181`).

### 14) ما العلاقة بين المقرر والامتحان؟
**One-to-Many**: مقرر واحد ← عدة امتحانات/مواعيد (`exam_schedule.course_id REFERENCES courses(id)` — `schema.sql:192`).

### 15) ما المقصود بـ One-to-One؟
**سجل واحد في جدول يقابله سجل واحد في جدول آخر**. نادرة هنا لأن النموذج عادة many.

### 16) أعطني مثالاً عليه من مشروعك إن وجد.
أمثلة شبه One-to-One: `teacher_course_files` بقيود `UNIQUE(teacher_id, course_id)` (`schema.sql:504`) و `course_vocabulary.course_id UNIQUE` (`schema.sql:487`) — كل (مفتاح) يقابل ملفاً واحداً فقط.

### 17) ما المقصود بـ One-to-Many؟
**سجل أبوي يقابله عدة سجلات فرعية** — الأكثر شيوعاً في التصميم. المفتاح الأجنبي يوضع في الجهة "العديدة".

### 18) أعطني مثالاً عليه من مشروعك.
- قسم → عدة محاضرين (`teachers.department_id`).
- مقرر → عدة حصص (`timetable.course_id`).
- تسليم → عدة صفوف منهج (`course_content_curriculum.submission_id`).
- مستخدم → عدة إشعارات (`notifications.user_id`).

### 19) ما المقصود بـ Many-to-Many؟
**كل طرف من الجانبين يقابله عدة أطراف من الآخر** — يتطلب جدول ربط (junction table) يحمل المفاتيح الأجنبية من الطرفين.

### 20) كيف يتم تمثيل Many-to-Many في قاعدة البيانات؟
عبر جدول ربط:
- `course_departments (course_id, department_id, semester)` — المقاررات ↔ الأقسام (`schema.sql:271`).
- `course_prerequisites (course_id, prerequisite_id)` — مقرر ↔ متطلباته (`schema.sql:263`).
- `user_roles (user_id, role)` — مستخدم ↔ أدوار (`schema.sql:42`).

### 21) لماذا لا تضع جميع بيانات النظام في جدول واحد؟
لأن ذلك يخلق:
- **تكراراً هائلاً** (اسم القسم يتكرر مع كل محاضر ومقرر).
- **تناقضاً** (نفس القسم بأسماء مختلفة).
- **صعوبة الحذف والتعديل** و**صعوبة الاستعلام**.
لهذا نصمم بالعلاقات.

### 22) ما المقصود بـ Normalization؟
**عملية تنظيم الجداول لإزالة التكرار والاعتماد** وتقسيم البيانات إلى جداول مترابطة وفق قواعد أشكال عادية (1NF, 2NF, 3NF).

### 23) ما المشكلة التي يحلها Normalization؟
- التكرار (Redundancy) — نفس المعلومة في عدة أماكن.
- شذوذ الإدخال/التحديث/الحذف (Anomalies) — مثل حذف بيانات مرتبطة سهواً أو تعديلها في مكان دون آخر.

### 24) كيف تمنع تكرار البيانات؟
- بوضع الكيان في جدوله (قسم واحد في `departments`) بدل تكراره نصياً.
- بواسطة `UNIQUE` (`courses.code`, `departments.name`, `users.username`).
- بواسطة علاقات FK بدل نص مكرر.
- فحص التكرار قبل الحفظ (مثل `_validate_code_updates` في `routes/courses.py`).

### 25) ما المقصود بـ Data Integrity؟
**صحة ودقة واتساق البيانات** في كل الأوقات — من خلال القيود (NOT NULL, UNIQUE, FK, CHECK) وتراخيص المنطق في الخدمات.

### 26) كيف تحافظ على سلامة البيانات؟
- `PRAGMA foreign_keys = ON` (`database/connection.py:25`).
- قيود `ON DELETE` موزونة (`CASCADE` للمحتوى التابع، `SET NULL` للمراجع الاختيارية مثل department).
- فحوصات قبل الحفظ في Service layer.
- سجل `history` (تدقيق) لكل العمليات الحساسة — `database/history.py` + `schema.sql:221`.

### 27) كيف تخزن بيانات المستخدمين؟
في `users` (`schema.sql:12`): username (فريد)، `password` **مجزأً بـ Werkzeug** `generate_password_hash` (ليست نص عادي!)، `role`، `email`، `department_id`، `is_active`، `force_password_change`. وقائمة أدواره في `user_roles`.

### 28) كيف تخزن بيانات أعضاء هيئة التدريس؟
في `teachers` (`schema.sql:50`): الاسم، البريد، الهاتف، القسم (`department_id` FK)، `academic_number`، `national_id`، المؤهل (`qualification_id`) والرتبة (`rank_id`) والتصنيف (`classification_id`) كمفاتيح أجنبية لقوائم مرجعية، و`user_id` لربط الحساب.

### 29) كيف تخزن المقررات؟
في `courses` (`schema.sql:72`): `code` (فريد عملياً)، `name`, `department_id`, `year`, `semester`, `theoretical_hours/practical_hours/total_hours`, `accreditation`, `vocabulary`, `syllabus_file`. وعلاقة الأقسام في `course_departments`.

### 30) كيف تخزن الجداول الدراسية؟
في `timetable` (`schema.sql:177`): `day`, `semester`, `course_id`, `teacher_id`, `room_id`, `period`, `department_id`, `student_section` (شعبة). مع نظام **إصدارات** `timetable_versions` لإصدارات الفصول النشطة (`status = 'active'|'superseded'`).

### 31) كيف تخزن الامتحانات؟
في `exam_schedule` (`schema.sql:190`): `course_id`, `department_id`, `exam_date`, `start_time/end_time`, `room_id`, `semester`, `status` (draft/submitted/...), `merged_at`, `published_at`, `signed_by_hod` (توقيع رئيس القسم)، مواعيد الجلسات في `period_settings` (`schema.sql:117`).

### 32) كيف تخزن الخطط الدراسية؟
الخطة تُعرض من **ربط المقررات بالأقسام والفصول** في `course_departments` مع `semester`، وتُنظّم في الواجهة في صفحة "الخطة الدراسية" `courses_list.js` (عرض `plans`). وبيانات المحتوى التفصيلية في `course_content_submissions`.

### 33) كيف تخزن الحضور؟
- حضور الطلاب: `attendance` (`schema.sql:255`) و`students`.
- حضور أعضاء هيئة التدريس: `faculty_attendance` (`schema.sql:279`): `teacher_id`, `date`, `status` (present/absent) — يديره رئيس القسم.

### 34) كيف تربط المقرر بالقسم؟
بطريقتين:
- عمود مباشر: `courses.department_id` (قسم أساسي).
- علاقة متعددة: `course_departments(course_id, department_id, semester)` — `schema.sql:271`. هذه هي الطريقة الحديثة لتدريس المقرر في أقسام متعددة.

### 35) كيف تربط عضو هيئة التدريس بالمقرر؟
عبر **جدول الجدول الدراسي `timetable`**: الحصة تحمل `course_id` و `teacher_id`، وعند الإنشاء تُسجل أيضاً في `teacher_taught_courses` (سجل تدريس الأستاذ) عبر `timetable_service._record_taught_course` (timetable_service.py:632). وكذلك `teacher_course_files` لملفات الأستاذ لكل مقرر.

### 36) كيف تمنع وجود سجل مرتبط بسجل غير موجود؟
بقيد **Foreign Key مع تفعيل `PRAGMA foreign_keys = ON`**: SQLite يرفض إدراج `timetable` بمقرر غير موجود. واختيار البيانات في الواجهة يأتي من جداول موجودة (Dropdown من قاعدة البيانات).

### 37) ماذا يحدث عند حذف سجل مرتبط بسجلات أخرى؟
يعتمد على `ON DELETE`:
- **CASCADE:** يُحذف التابع مع الأب (حذف مقرر → حذف حصصه: `timetable.course_id ... ON DELETE CASCADE`).
- **SET NULL:** يصبح العمود NULL (حذف قسم → `department_id = NULL` في المحاضر).
- **RESTRICT/NO ACTION:** يمنع الحذف إذا بقيت سجلات تابعة.
- المشروع يهيئ ترحيلاً يجعل كل FK نحو `departments` بـ `SET NULL` (schema.py:435 `_migrate_department_fks`).

### 38) كيف تحمي بيانات المستخدمين داخل قاعدة البيانات؟
- **كلمات المرور مجزأة** (`generate_password_hash` — لا تُخزن نصاً).
- واجهة API تحذف الحقول الحساسة (`public_user` في `api/helpers.py:61` تحذف أي عمود يحوي password/token).
- الـ session موقعة بـ `SECRET_KEY` (config.py:12) مع HttpOnly.
- CSRF لكل طلبات التغيير (`security/csrf.py`).
- هيدرات أمنية + سياسة CSP (`app.py:300-335`).

## المدرس الرابع: JavaScript

> صفحات المشروع المبنية بالمكونات التفاعلية: `templates/courses_list.html`, `templates/courses/codes.html`, `templates/teachers/list.html`, `templates/timetable/management.html`, `templates/exams/*.html`, وأصولها JS في `static/js/` (خاصة `spa/api.js` و`courses_list.js`).

### 1) لماذا استخدمت JavaScript في المشروع؟
لجعل الواجهة **تفاعلية دون إعادة تحميل الصفحة**: فتح/إغلاق نوافذ (Modal/Drawer)، فلترة المقررات، إرسال البيانات عبر `fetch`، معالجة список (dropdown)، pagination، وأيقونات المقررات. هذا يحسّن سرعة الاستخدام ويجعل صفحة المقررات تبدو كتطبيق SPA.

### 2) ما الفرق بين JavaScript وPython؟
- **JavaScript:** تعمل في **المتصفح**، تتعامل مع DOM والأحداث والـ UI، نوع ديناميكي.
- **Python:** تعمل في **السيرفر**، تتعامل مع قاعدة البيانات والمنطق والأمان والأدوار.
- التواصل بينهما هنا عبر **fetch + JSON** — JS ترسل، Flask يستقبل ويرد.

### 3) ما هو DOM؟
**Document Object Model** — تمثيل هرمي لصفحة HTML في الذاكرة؛ كل عنوان/زر/جدول هو "عقدة". JavaScript تتعامل معه لتعديل الصفحة. عندما يستدعي `document.getElementById('...')` فأنت تلمس الـ DOM.

### 4) لماذا نحتاج إلى DOM؟
بدونه لا يمكن للـ JavaScript **قراءة قيم حقول** أو **تغيير محتوى** أو **إظهار وإخفاء** عناصر حسب تفاعل المستخدم — أي لا تفاعلية. مثال: `courses_list.js` يقرأ `document.getElementById('planTableBody')` ويعيد بناء صفوفه.

### 5) كيف تصل JavaScript إلى عنصر HTML؟
بواسطة:
- `document.getElementById('id')` (الأكثر استخداماً في المشروع).
- `document.querySelector('.class')`.
- `document.querySelectorAll(...)`.
- `flatCourses()` في `courses_list.js:170` هو مثال مطابق على الاستعلام وربطه بالحالة.

### 6) ما هو Event؟
حدث يحدث في المتصفح: `click`، `change`، `submit`، `keyup`، `DOMContentLoaded`. في المشروع: `click` على أزرار الفلترة، `change` على اختيار الفصل، `submit` على نماذج الرفع.

### 7) ما هو Event Listener؟
**دالة مسجلة تصغي لحدث معين** على عنصر معين وتنفذ عند وقوعه. مثال:
```js
document.getElementById('searchInput')?.addEventListener('input', handleSearch);
```
`courses_list.js` (بحث فوري). فأي Input يعيد بناء القائمة.

### 8) كيف تجعل زراً ينفذ وظيفة عند الضغط عليه؟
```js
btn.addEventListener('click', () => { ... });
```
في صفحة المقررات: أزرار فتح المودال للتعديل تسجل بهذا الأسلوب (handleEdit/openModal)، وزر "التالي" في المعالجات. كما يُستخدم `onclick="openModal(...)"` في القوالب مباشرة لبعض الأزرار.

### 9) ما الفرق بين let وconst؟
- **const:** لا يمكن إعادة الإسناد بعد الإنشاء (القيم تُستخدم دائماً للثوابت المرجعية). متوقع: `const maximum = 10;` في `courses_list.js:31`.
- **let:** يمكن إعادة الإسناد (المتغيرات المتغيرة مثل فهرس التشغيل).
- **var:** قديم، غير مستحسن لسلوك النطاق الغامض — المشروع لا يستخدمه.

### 10) ما هي Function في JavaScript؟
**كتلة كود قابلة لإعادة الاستخدام** — إما:
- `function getPageData() { ... }` (إعلان).
- أو `const getItems = () => { ... }` (سهم = arrow).
`courses_list.js` مليء بها: `handlePageClick`, `handleSearch`, `switchCodesView`.

### 11) ما هو Array؟
**قائمة مرتبة** من القيم: `[1,2,3]`. مع دوال جاهزة مثل `filter`, `map`, `forEach`, `push`.

### 12) ما هو Object؟
**مجموعة من أزواج (مفتاح: قيمة)** `{ name: 'faiz', id: 3 }` — يستخدم لتخزين صفوف البيانات القادمة من Flask.

### 13) أين استخدمت Arrays في مشروعك؟
- `allCourses` المصفوفة المركزية لكل مقررات الصفحة (في `courses_list.js`).
- مصفوفة الأسابيع: `[ 'الأول', 'الثاني', ... 'الثاني عشر' ]` لجدول الساعات (`weeks array` في كود جدول المحتوى).
- مصفوفة grid data في صفحة المحتوى (`gridData`)، وقائمة الأقسام في dropdown.

### 14) أين استخدمت Objects؟
- `const container = { name: 'departments', label: 'الأقسام', ... }` في `courses_list.js:32`.
- صفوف البيانات: كل مقرر `{ code: 'ت209', name: 'رياضيات', ... }`.
- `gridData[id]` كقاموس لتخزين محتوى كل خلية في جدول الأسابيع.

### 15) ما وظيفة fetch()؟
**إرسال طلب HTTP من JavaScript إلى السيرفر** وإرجاع Promise:
```js
return fetch(url, { method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-CSRFToken': ... },
  body: JSON.stringify(payload) });
```
المشروع يغلّف هذا في `static/js/spa/api.js` (`apiFetch` / `postJson`).

### 16) لماذا قد تستخدم fetch() بدلاً من إعادة تحميل الصفحة؟
لأنها تحدث **جزءاً فقط** من الواجهة بدون Refresh كامل: أسرع، تحافظ على حالة الصفحة، وتمكن تفاعلات متعددة متتالية. مثال: زر "اعتماد الحذف" في صفحة المقررات يرسل DELETE ثم يحدّث الصف فقط.

### 17) ما هو AJAX؟
**Asynchronous JavaScript And XML** — تقنية قديمة تعني "طلبات سيرفر غير متزامنة من المتصفح دون إعادة تحميل". fetch() هي **البديل الحديث** له — والمشروع يعتمد fetch فقط.

### 18) ما العلاقة بين AJAX وfetch()؟
- AJAX: المفهوم العام (الطلب غير المتزامن).
- fetch: **الأداة الحديثة** لتحقيق هذا المفهوم في متصفحات اليوم (بدل XMLHttpRequest القديم).
- أي استخدام fetch في المشروع هو تطبيق لـ AJAX عملياً.

### 19) ما هو JSON؟
**صيغة نصية لتبادل البيانات**: `{ "key": "value" }` — يفهمها كل من JavaScript وPython بسهولة. هي "اللغة المشتركة" بين `static/js` والسيرفر Flask.

### 20) كيف تتعامل JavaScript مع JSON القادم من Flask؟
- Flask يرد بـ `jsonify({ok: true, data: ...})`.
- `parseOk`/`apiFetch` في `spa/api.js` تنفذ `resp.json()` وتقرأ الحقل `ok`، وفي الفشل تقرأ `message` للعرض.
- مثال الاستخدام: `if (result.ok) { ... } else { alert(result.message); }` في `courses_list.js`.

### 21) كيف ترسل JavaScript بيانات إلى Flask؟
عبر fetch مع `body: JSON.stringify(...)`:
```js
apifetch('/api/plans/create', { method: 'POST', body: JSON.stringify({ name, departments: [...] }) })
```
`static/js/spa/api.js` تحقن تلقائياً `X-CSRFToken` في الرؤوس.

### 22) كيف تستقبل Flask البيانات المرسلة من JavaScript؟
عبر `request.get_json()`:
```python
data = request.get_json(silent=True) or {}
name = data.get('name', '')
```
مثال في `api/plans.py:14-18` (إنشاء خطة دراسية) و`api/questions.py` و`api/exams.py` — كلها JSON APIs.

### 23) كيف تحدث جزءاً من الصفحة بدون Reload؟
تنفيذ `fetch` ثم تحديث DOM فقط:
1. أرسل الطلب.
2. في `then` اضبط DOM (أضف صفاً، أعد إنشاء الجدول، أغلق modal).
مثال: بعد حفظ مقرر جديد في `courses_list.js` يُعاد إنشاء جدول المقررات (function render) دون reload.

### 24) كيف تعاملت مع الـ Modal؟
نمط (HTML مخفي + JS):
- في القالب عنصر `div` بـ `hidden` (مثل `#courseModal` في `courses_list.html`).

### 29) ماذا يحدث عند الضغط على زر تحميل أو حفظ في واجهة تعتمد على JavaScript؟
1. `submit` event يلقطه listener (مع `preventDefault`).
2. تجميع البيانات من الحقول + CSRF.
3. `fetch` إلى المسار JSON (`/api/...`).
4. على النجاح: أغلق modal + حدّث DOM (`refreshData()`).
5. على الفشل: اعرض `result.message` للتوضيح.
كل هذا يتجنب إعادة تحميل الصفحة.

### 30) إذا لم يعمل Event Listener، ماذا تفحص؟
1. هل العنصر موجود وقت التسجيل؟ (لهذا نستخدم `document.addEventListener('DOMContentLoaded', ...)` — أو `?.` — حتى لو تأخر الـ DOM).
2. هل معرّف/فئة العنصر مطابق؟ (`id` في HTML مقابل `getElementById`).
3. هل الكود محمّل أصلاً (مسار الصفحة)؟
4. **خطأ شائع معروف في المشروع:** `switchCodesEditorMode` تقرؤها صورتان متعارضتان (تعريفان في ملفات/أسطر مختلفة) — انظر ملخص الأخطاء في نهاية الدليل.

### 31) إذا لم يرجع fetch() البيانات المتوقعة، كيف تبحث عن المشكلة؟
- افتح **Network tab** في DevTools: هل الحالة 200/201/403/422؟
- اقرأ `resp.json()` وافحص `ok` و `message` — api/helpers.py يعيد هذه البنية.
- **403/CSRF:** تأكد أن `X-CSRFToken` أُرسل؛ `spa/api.js` يقرأ التوكن من `localStorage`/hidden field.
- **401:** الـ fetch يلتقطه ويوجّه للجلسة — معالج `401` في `spa/api.js`.

### 32) كيف تتعامل مع الأخطاء في JavaScript؟
- `try/catch` حول `await apiFetch(...)` في `spa/api.js`.
- معالجة الشبكة: `catch` يعرض رسالة "حدث خطأ غير متوقع".
- في المشروع اعتمدنا على رد `{ok:false, message}` من السيرفر لإظهار رسائل صديقة للمستخدم.

### 33) ماذا يحدث إذا حذفت Event Listener من زر؟
الزر يصبح **بلا وظيفة** — الضغط عليه لا شيء. وهذا قد يكون صامتاً (بدون خطأ) لو لم يوجد خطأ في طريقة التسجيل. لذلك يجب التحقق من الاقتران الصحيح بين `id` في القالب و `.addEventListener` في JS.

### 36) كيف تتعامل JavaScript مع تغيير الفصل الدراسي؟

### 37) كيف تعرف JavaScript أن المستخدم اختار مادة معينة؟

## المدرس الخامس: HTML / CSS / Frontend

### 1) ما دور HTML في مشروعك؟
**هيكل الصفحات** (بنية): العناصر — الأزرار، الجداول، النماذج، القوائم. كلها في `templates/` بصيغة Jinja2. القالب `base.html` يعطي الهيكل العام، وكل صفحة تملأ القوالب `{% block %}`.

### 2) ما دور CSS؟
**التصميم والمظهر**: الألوان، التباعد، الخطوط، التفاعلية (hover)، الوضع الليلي، والتجاوب مع شاشات الهاتف. المشروع يعتمد على Bootstrap 4.6 + Tailwind (CDN) بالإضافة لملف `static/css/style.css` ومتغيرات CSS المخصصة.

### 3) ما دور JavaScript؟
**السلوك التفاعلي** داخل الصفحة: فتح النوافذ، الفلترة الفورية، التواصل مع السيرفر عبر fetch، وتحديث الجداول دون إعادة تحميل — تفصلها عن HTML تماماً كما تُفصل المظهر.

### 4) ما الفرق بين HTML وCSS؟
- **HTML** = الحركة/الهيكل: "هذا زر، هذا جدول".
- **CSS** = المظهر: "هذا الرمز أحمر، وهذه مسافة p-4".
مثال: `<button class="btn btn-primary">حفظ</button>` — HTML يحدد Button، وCSS تحدد `btn`.

### 5) ما المقصود بـ Semantic HTML؟
استخدام **وسوم ذات معنى** (`header`, `nav`, `main`, `table`, `form`, `aside`) بدل `<div>` عشوائي. الفائدة: سهولة القراءة، وتحسين الوصول (Accessibility) ومحرك البحث. مثال: `templates/shared/layouts/base.html` يستخدم `<aside>`, `<nav>`, `<main>` في تخطيط لوحة التحكم.

### 6) لماذا نستخدم form؟
لأنها **حاوية تجميع بيانات الإدخال وترسلها إلى السيرفر** (GET/POST): الـ fields + زر submit + `action` + `method`. كل نماذج المشروع مثل OTP/تسجيل الدخول forms: `<form method="post" action="{{ url_for('auth.login') }}">`.

### 7) ما وظيفة input؟
حقل إدخال نصي/رقمي/إلخ. `name` تحدد مفتاح التخزين و `type` نوعه. مثال `<input type="text" name="username" required>` — بعد الإرسال تُقرأ عبر `request.form['username']`.

### 8) ما الفرق بين أنواع الـ Input؟
- `text` نص، `password` يخفي الأحرف (ملكية). تستخدم في `login.html`.
- `number` إدخال رقمي، `date` تاريخ، `file` ملفات (مع `enctype`).
- `checkbox` خانات، `radio` اختيار واحد. الـ `hidden` تخزن توكن CSRF.

### 9) لماذا نستخدم label؟
تربط `for="id"` نصة عنوان بحقل الإدخال — **إمكانية الوصول**: النقر على النص يفعل الحقل، وقارئ الشاشة يقرأ اسم الحقل. مثال: `<label for="username">اسم المستخدم</label>`.

### 10) ما أهمية button؟
**زر إرسال/تنفيذ إجراء**. `<button type="submit">` في form يرسل البيانات، و `<button type="button">` إجراءات JS (فتح modal). بدونها لا يمكن تنفيذ أي تفاعل. في المشروع قوالب تستخدم `onclick="window.location.href='...'"` أيضاً.

### 11) كيف تنشئ جدولاً باستخدام HTML؟
```html
<table>
  <thead><tr><th>اسم</th><th>القسم</th></tr></thead>
  <tbody><tr><td>...</td><td>...</td></tr></tbody>
</table>
```
والـ tfoot في `courses_list.html` يحتوي أزرار pagination — ربط جدول الصفحة.

### 12) لماذا استخدمت Tables في بعض أجزاء النظام؟
لعرض **بيانات مقعدة**: قوائم المقررات والأساتذة والجداول. يُكمل Piggyback للحصول على `thead/tbody/tfoot` المناسب — أي عرض الجداول ببنية واضحة مع Pagination في tfoot.

### 13) كيف أنشأت نماذج إدخال البيانات؟
بـ HTML form + حقول input + validation attribute (required) + CSRF مخفي:
```html
<form method="post" action="...">
  <input name="_csrf_token" type="hidden" value="{{ csrf_token() }}">
  ...
</form>
```
وسيرفر Flask يعيد التحقق ويتحقق من CSRF في `security/csrf.py:93`.

### 14) كيف تتحقق من البيانات المدخلة؟
- **على المتصفح:** `required`, `min`, `maxlength`, placeholder «عددHeart؟» تمت in layout: سطر `required` في حقول النماذج.
- **على السيرفر (الأهم):** validate_* في `routes` + `api/helpers.py` + `core/validation.py`. المتصفح يمكن تجاوزه — الأمان عند السيرفر.

### 15) ما المقصود بـ Accessibility؟
**دعم الوصول** لذوي الاحتياجات: تسميات (label)، تباين، انتقال عبر Tab، نص بديل، ARIA، صلة بـ `aria-label`. ابحثها في `base.html` و`teachers/list.html:173` (توابع Drawer).

### 16) كيف راعيت Accessibility في المشروع؟
- `label for` لكل حقول النماذج.
- `aria-label` و `aria-expanded` للقوائم (مثل زر تبديل الوضع الليلي في `base.html:68`).
- تباين ألوان عبر متغيرات CSS (`--primary`, `--text...`) مع دعم Dark Mode.
- `dir="rtl"` و `lang="ar"` لإعلان اللغة الاتجاهي (head_preamble.html:2).

### 17) ما المقصود بـ RTL؟
**Right-To-Left** — اتجاه عرض من اليمين لليسار، مطلوب للغة العربية. يُعلن في HEAD: `<html lang="ar" dir="rtl">` (`head_preamble.html:2`).

### 18) لماذا واجهة مشروعك RTL؟
لأن النظام **موجه للكلية الليبية** وكل محتواها بالعربية — يجب أن تظهر كل النصوص والقوائم من اليمين. أعمل أيضاً بمظلل CSS `[dir="rtl"]` لضبط الهوامش والتباعد في المواضع العربية.

### 19) كيف تجعل الصفحة Responsive؟
- Grid/Flex عريض (Bootstrap) + Tailwind `grid-cols-1 md:grid-cols-2 lg:grid-cols-3`.
- viewport meta: `<meta name="viewport" content="width=device-width, initial-scale=1">` في head_preamble.html.
- Sidebar قابل للطي على الموبايل: `sidebar-overlay` + دالة `openSidebarMobile()` في `base.html:13`.

### 20) ما المقصود بـ Flexbox؟
**نظام تنسيق أحادي البعد** (صف أو عمود) لتوزيع العناصر وتوسيطها: `display:flex`, `justify-content`, `align-items`, `gap`. أمثلة في `base.html` للأزرار القائمة الجانبية وصفوف البطاقات.

### 21) ما المقصود بـ CSS Grid؟
**نظام تنسيق ثنائي الأبعاد** (صفوف+أعمدة) للشبكات: `display:grid; grid-template-columns: ...`. أمثلة: درع المقررات وبطاقات department.

### 22) متى تستخدم Flexbox ومتى تستخدم Grid؟
- **Flexbox** عند التوزيع على محور واحد (شريط أزرار، رأس).
- **Grid** عند الشبكة الحقيقية (صفوف وأعمدة متزامنة، مثل شبكة بطاقات المقررات `grid grid-cols-2 md:grid-cols-4`).
في المشروع: Flex لرأس الجدول، Grid لشبكة البطاقات.

### 23) ما المقصود بـ Responsive Design؟
**تصميم يتكيف مع أي عرض شاشة** (هاتف/تاب/حاسوب) دون كسر للمحتوى أو نزوح العناصر — عبر وحدات نسبية ونقاط إيقاف (breakpoints) وإخفاء/إظهار العناصر. `sidebar no-sidebar` هو تطبيق مباشر لذلك.

### 24) كيف تجعل الواجهة تعمل على الهاتف والكمبيوتر؟
- نقاط الإيقاف في CSS (`sm/md/lg`) الخاصة بـ Bootstrap/Tailwind.
- الصفوف "التناددية" (flex-wrap / grid-cols responsive).
- القائمة الجانبية تنهار إلى Overlay عند الشاشات الصغيرة (`toggleSidebar`).

### 25) ما هو Tailwind CSS؟
**إطار CSS وظيفي** — تصنيفات متعدد الأغراض الصغيرة تعمل كـ CSS مباشرة في HTML: `flex`, `p-4`, `grid`, `hidden`, `text-sm`. حمّلناه عبر CDN في `base.html`.

### 26) لماذا استخدمت Classes جاهزة في التصميم؟
لأنها **تكتب CSS أقل، والتصميم موحد ويتحدث سريعاً** بدون كتابة قواعد CSS مخصصة لكل عنصر. فالبنية والوظيفة تركز في العلامات.

### 27) ماذا يعني class مثل flex؟
`flex` = `display: flex;` — يحول العنصر إلى حاوية Flexbox توزع أبناءه في ترتيب مرن (أفقي بالعربية RTL).

### 28) ماذا يعني grid؟
`grid` = `display: grid;` — يحول العنصر إلى Grid، مع أعمدة محددة بصفوف إضافية مثل `grid-cols-3`.

### 29) ماذا يعني p-4 أو px-4 في Tailwind؟
- `p-4` = padding في الاتجاهات الأربعة بمقدار 1rem (المقياس المستخدم 4px×4).
- `px-4` = padding أفقي فقط (يمين+يسار). هذا النظام يضمن التباعد الموحد.

### 30) كيف صممت الـ Cards؟
`card`/البطاقة نمط:
```html
<div class="card">
  <div class="card-header">...</div>
  <div class="card-body">...</div>
</div>
```
للوحات البيانات والعناصر المعروضة داخل النوافذ (مثل "بطاقات الاعتماد" و "بطاقات المحتوى الدراسي" pod الموظف).

### 31) كيف صممت الـ Drawer؟
لوحة منزلقة مثبتة: `class="fixed inset-0 z-50 hidden" dir="rtl"` لعنصر ظاهر/علوي ثم خلفه `backdrop`. JS يفتحه بإزالة `hidden` ويغلق بإعادتها (مثل `openAssignDrawer` في `teachers/list.html:172`).

### 32) كيف صممت الـ Modal؟
Modal: طبقة كحجاب `relative` + صندوق مركز `absolute`، إغلاق بزر، إلغاء عبرEsc، خلفية Overlay. البيانات تُملأ من JS (`openModal(record)` في `courses_list.html`).

### 33) كيف صممت القوائم والجداول؟
- القوائم: `<nav>` بـ flex (القائمة الجانبية في `base.html`)، والـ Dropdown مخصص.
- الجداول: `table` حقيقي مع `thead` لإعادة تنظیم، و صفوف tbody `hover`، وقسم tfoot للـ Pagination.

### 34) كيف حافظت على تناسق الواجهات؟
- استخدام `base.html` (هيكل موحد) لكل الصفحات.
- الدوال والأصناف المشتركة (`btn`, `badge`, `card`) في `style.css`.
- نفس `keywords` CSS/variables (`--primary`) لكل لوحة.
- سياق مشترك من التسجيل: navbar و sidebar وأنماط نفسها لكل الأدوار.

### 35) ماذا يحدث إذا حذفت CSS Class مهمة؟
يختل **المظهر** فقط — قد تظهر عناصر بلا تباعد/اختصاص، أو يزيل `hidden` فيظهر عنصر مقصود: "الواجهة شوهدت" لكن **الوظائف و الأمان لا يتأثران** (الحماية في السيرفر).

### 36) كيف تجعل النصوص العربية تظهر بشكل صحيح؟
- `lang="ar" dir="rtl"` في `<html>` (`head_preamble.html:2`).
- استخدام الخطوط المناسبة (Cairo/حفز) من Google Fonts وتفعيل `font-family` في CSS.
- اختبار النقاط/القصاصة بشكل إضافي في محركات الاعتماد/الطباعة (مثل `_print_document.html`).

### 37) كيف تعاملت مع الشاشات الصغيرة؟

### 38) لماذا فصلت HTML عن CSS وJavaScript؟
**مبدأ ××فصل المسؤوليات (Separation of Concerns)**:
- HTML: البنية.
- CSS: المظهر.
- JS: السلوك.
الفوائد: صيانة أسهل (عدل CSS دون HTML)، إمكانية إعادة استخدام الملفات، ومشاركة واضحة لكل ملف. المشروع: `templates/`, `static/css/style.css`, `static/js/*.js`.

## المدرس السادس: Backend

### 1) ما المقصود بالـ Backend؟
الجزء من التطبيق الذي يعمل **على السيرفر**: معالجة الطلبات، التحقق، الصلاحيات، القراءة والكتابة في قاعدة البيانات، وتجهيز البيانات. كل شيء يقع في `routes/` و`services/` و`security/` و`database/` — لا يراه المستخدم مباشرة.

### 2) ما الفرق بين Frontend وBackend؟
- **Frontend:** ما يظهر للزائر في المتصفح — HTML للهيكل، CSS للمظهر، JS للتفاعل (`templates/`, `static/`).
- **Backend:** ما يعمل على السيرفر — المنطق، الأمان، والتخزين (`routes/`, `services/`, `database/`).
- مثال: صفحة تسجيل الدخول — حقلي HTML (Frontend) في مقابل التحقق من كلمة المرور (Backend).

### 3) ماذا يحدث عندما يضغط المستخدم على زر في الموقع؟
1. المتصفح يشغّل حدث (click/submit).
2. إما JavaScript يرسل fetch (SPA) أو الحقول form تُرسَل كـ POST عادي.
3. المتصفح يرسل HTTP Request إلى عنوان الـ route.
4. السيرفر (Flask) يعالج، يتحقق، يخزن/يقرأ، ثم يرد.
5. المتصفح يعرض الرسالة الجديدة أو يعيد بناء القسم.

### 4) كيف يصل الطلب من المتصفح إلى Flask؟
عبر بروتوكول **HTTP**: المتصفح ينشئ Request إلى (المضيف/المنفذ/المسار) المحدد في `url_for` مثل `/courses/plan`، ثم Flask يستقبله من خلال WSGI server (المدمج في التطوير، Waitress في الإنتاج — `serve.py:57`).

### 5) كيف يستقبل Flask الطلب؟
يستدعي **دالة الـ view المرتبطة بالمسار** بعد فحص الـ middleware:
```python
@bp.route('/plan', methods=['GET', 'POST'])  # routes/courses.py:47
```
قبل الوصول للدالة يمر `before_request` (فحص CSRF + security headers) في `app.py:174-240`.

### 6) كيف يحدد Flask الـ Route المطلوب؟
Flask يطابق **المسار + طريقة الطلب** مع خريطة الـ rules المسجلة في كل `@route`. المسارات المُعلنة (`url_prefix='/courses'`, `/teachers`, `/exams`...) توزع التنفيذ بصورة طبيعية. وإن لم يوجد يُرجع 404.

### 7) ماذا يحدث داخل الـ Route؟
داخل دالة الـ view:
1. فحص الصلاحية (`@permission_required`).
2. قراءة `request` (form/args/json).
3. استدعاء Service (business logic).
4. بناء البيانات ثم `render_template(...)` أو `redirect` أو `jsonify`.

### 8) كيف يتم التحقق من المستخدم؟
- الـ decorator `@login_required` ينفذ فحص `'user_id' in session` (`security/authorization.py:133`).
- بيانات المستخدم تُجلب من القاعدة عبر `get_user()` في `security/auth.py:17` (بفحص `session['user_id']`).
- إذا غير مسجل → تحويل إلى `/login`.

### 9) ما الفرق بين Authentication وAuthorization؟
- **Authentication:** إثبات الهوية (من أنت؟) — تسجيل الدخول بكلمة مرور.
- **Authorization:** تفويض الأفعال (ماذا تسمح له؟) — `@permission_required`.
- كلاهما منفصلان في الكود: مصادقة في `user_service`، تفويض في `security/authorization.py`.

### 10) كيف طبقت Authentication في مشروعك؟
في `user_service.py:85-181` (`authenticate`):
1. قراءة username/password من `request.form`.
2. `find_by_username`.
3. `check_password_hash(user.password, password)`.
4. إذا صحيح: تخزين `session['user_id']`, roles... وإلا إرجاع خطأ.

### 11) كيف طبقت Authorization؟
بنظام permissions:
```python
roles = get_granted_roles()
if not has_permission(roles, required_perm, dept_id):
    return redirect(...)
```
- في `security/authorization.py:147` (`@permission_required`) و `enforce_permissions` في `app.py:174` (قبل كل طلب، deny-by-default).

### 12) ما هو Role؟
**هوية وظيفية** داخل الكلية: `research_development`, `faculty_affairs`, `head_of_department`, `teacher`, `exam`, `dean`, `visitor` — المعرفة في `core/constants/roles.py`.

### 13) ما هو Permission؟
**إذن لعمل محدد**: `courses.manage`, `timetable.edit`, `exams.manage`, `teachers.manage`, `content_pack.publish`, وغيرها. تُتبنى كمفاتيح صحيحة وقابلة للتوسعة في `core/constants/permissions.py:16` (`ROLE_PERMISSIONS`).

### 14) كيف يعرف النظام أن المستخدم Teacher؟
عند تسجيل الدخول تُخزن كل أدواره في `session['roles']`، والدور النشط في `session['role']`. الفحص في `security/authorization.py:180`: `if session.get('role') in allowed_roles:`. ويؤكده `user_service.find_roles_by_user` عند كل طلب.

### 15) كيف يعرف النظام أن المستخدم Head of Department؟
بالإضافة للدور `head_of_department`، نفحص **قسم الرئاسة**: `session.get('hod_department_id')` — مثلاً في `hod_pages.py` يتحقق `if session.get('role') != 'head_of_department'` ويعيد 403 للمدارس الأخرى. وهنا جدول `departments.hod_id` يحدد رئيس القسم.

### 16) كيف تمنع Teacher من الوصول إلى صفحة Admin؟
بدورها:
- الصفحات الإدارية تحمل `@permission_required('courses.manage')` — ولا يملكها الـ teacher (انظر `ROLE_PERMISSIONS`).
- طبقة `enforce_permissions` في `app.py:174` ترفض أي مسار بلا صلاحية معلنة.
- إذا حاول يدوياً كتابة URL → يُحال 403 (أو redirect للوحة).

### 17) هل إخفاء الزر يكفي لحماية الصفحة؟ ولماذا؟

## اللجنة العملية (أمام الحاسوب أو الكود)

### 1) لو حذفت هذا الـ decorator من Route، ماذا سيحدث؟
- حذف `@permission_required('x')`: الطلب يجرب الوصول لكن قطارة الأمان العامة `enforce_permissions` في `app.py:174` — بما أن المسار لم يعلن أي صلاحية — تتفاعل وفق سياسة **deny-by-default** — أي يُرفض الطلب فوراً. (لا أزيلها إلا وأنا أثبت أن المسار عام).
- حذف `@login_required`: المستخدم غير المسجل يصل للدالة وقد تنهار/تحصل قراءة session فارغة — خطأ أمان محتمل.

مثال: `if session.get('role') != 'head_of_department'` (في `hod_pages.py`) — لضمان أن **رئيس القسم المحدد فقط** يكمل تعديل محاضر قسمه، وأي مستخدم آخر يمنع. الأهداف النموذجية: منع تعارض، منع صلاحية، منع تكرار، منع وصول غير مصرح.

### 3) من أين جاءت هذه البيانات؟
سؤال يُجيب عليه مسار البيانات:
- من القاعدة: `get_db().execute(...)` (داخل Service/Repository).
- من الـ request: `request.form.get(...)` / `request.get_json()`.
- من الجلسة: `session.get('role')` / `current_user()`.
- من القالب: متغير مرّر في `render_template`.

طبقة كامل الشاشة (`fixed inset-0 z-50 hidden` RTL) تفتح بزر: JS تزيل `hidden` (تظهر اللوحة)، وتغلق بإضافة `hidden` أو بالضغط على close/x أو الـ backdrop. مثال `templates/teachers/list.html:172` (تكليف أستاذ).

### 29) كيف يفتح Modal؟
`openModal(record)`: ملء لحقول (id/title/name/values) وإزالة `hidden`، ووضع تركيز. و`closeModal()` يعيدها للإضافة لاحقاً. هذه الإشكالية قلبت المبدأ — جرّبه في `courses_list.html`.

### 30) كيف ترسل JavaScript البيانات إلى Flask؟
```js
apiFetch('/api/plans/create', { method:'POST', body: JSON.stringify(payload) })
```
حيث `apiFetch` في `spa/api.js` تضيف `X-CSRFToken` تلقائياً وترفع `Content-Type`. السيرفر يستقبل عبر `request.get_json()`.

### 31) كيف تستقبل JavaScript نتيجة Flask؟
`const result = await resp.json();` ثم:
- النجاح: `ok:true` → تحديث DOM/رسالة.
- الفشل: `ok:false` → عرض `result.message`.
البنية موحدة في `api/helpers.py:80` و`api/helpers.py:87`.

### 32) لماذا استخدمت JSON هنا؟
لأن JSON خفيف، يفهمه JS وPython مباشرة، ويتحمّل البنية الهيكلية (كائنات/مصفوفات). للردود البسيطة أستفيد من `jsonify(ok=True, data=...)` لتناسق واجهات API سهل في الاختبار.

### 33) ماذا يحدث إذا فشل fetch()؟
- شبكة/سيرفر: `catch` في `spa/api.js` يعرض "فشل الاتصال" ولا ينكسر التطبيق.
- فشل عمل منطقي: السيرفر يرجع `{ok:false,message}` → JS يظهر الرسالة فقط.
- 401: fetch يوجّه لتسجيل الدخول تلقائياً (معالَج للجلسات المنتهية).
- 403/CSRF: رسالة صريحة.

### 34) ماذا يحدث إذا أعدت تحميل الصفحة بدلاً من استخدام AJAX؟

### 1) أنت قلت إنك استخدمت Flask، أرني أين استخدمته.
قل: "افتح `app.py` — هنا `create_app()` (سطر 92)، وتسجيل Blueprints مثل `bp = Blueprint('courses', ...)` في `routes/courses.py`. وكل صفحة في النظام route عليها decorator من Flask."

### 2) أنت قلت إن عندك صلاحيات، أين طبقتها في الكود؟
أشر إلى `security/authorization.py:147` (`@permission_required`) و`core/constants/permissions.py:16` (`ROLE_PERMISSIONS`) و`app.py:174` (enforce_permissions). وأعطي مثالاً فورياً: صفحة الاعتماد `course_content` تتحقق `content_pack.something`.

### 3) قلت إن النظام آمن، ما الذي فعلته فعلياً لحماية النظام؟
- كلمات المرور مجزأة (Werkzeug) لا نصية.
- `@login_required/@permission_required/@role_required` + deny-by-default لكل طلب (`app.py:174`).
- CSRF لكل طلبات تغيير الحالة (`security/csrf.py:93` + `STATE_CHANGING_METHODS`).

### 4) قلت إنك تستخدم قاعدة بيانات، كيف يرتبط هذا الجدول بهذا الجدول؟
أشر بالجدول: "جدول `timetable` به `course_id REFERENCES courses(id) ON DELETE CASCADE` (schema.sql:181) — أي حصة لمقرر محذوف تحذف تلقائياً. وهنا `users.department_id REFERENCES departments(id)` (schema.sql:18)."

### 5) قلت إن JavaScript يتواصل مع Flask، كيف؟
"عبر fetch متجه إلى `/api/...` — JS يرسل JSON مع CSRF، Flask يستقبل بـ `request.get_json()` في `api/helpers.py` ويعيد `{ok, data}` عبر `jsonify`. أشرح: زر يحفظ مقرر → `handleSubmit` في `courses_list.js:62`."

### 6) لو حذفت هذا السطر، ماذا يحدث؟
أسلوب الجواب: أحدد أثره مباشرة.
- حذف `@permission_required` → لا فحص صلاحية لهذا المسار (إلا بالطبقة العامة).
- حذف `db.commit()` → العملية تظل غير منفذة نهائياً (تبقى داخل معاملة pending).
- حذف `session.clear()` من logout → المستخدم لا يخرج فعلياً.

### 7) لماذا كتبت الكود بهذه الطريقة؟
أية شريحة تُسأل، أسباب عامة أذكرها: الفصل الطبقي (routes/services/db)، إعادة الاستخدام، الأمان (decorators + param queries)، والوضوح. ثم أستدل على السبب الخاص: "هنا فصلت الحلقة في Service ليعاد استخدامها مع الواجهة و API".

### 8) هل كان بإمكانك تنفيذها بطريقة أخرى؟
نعم أفصح ببديل وأبرر سبب ما اخترت:
- SQLite بدل PostgreSQL → أسهل استضافة ودائمة مع الكلية.
- Jinja2 SSR بدل React SPA كامل → مشروع أداء كافٍ وعمل بلا build tooling، مع استخدام fetch للمكالمات التفاعلية فقط.
- التحقق اليدوي بدل WTForms → سيطرة كاملة وسهولة قراءة.

### 9) ما المشكلة التي يحلها هذا الجزء من الكود؟
أجيب بوظيفة السطر:
- `enforce_permissions` تحل مشكلة "صفقة أمان مضمونة لكل المسارات".
- `check_teacher_availability` تحل "تعارض المحاضرات في الجدول".
- `apply_transition` تحل "التحكم بسير عمل المحتوى (من رفع إلى نشر)".
كلها مشاكل حقيقية واجهتها عند البناء لا مجرد روتين.

### 10) أعطني مثالاً حقيقياً من مشروعك.
جاهز ثابت: "عندما يسجل محاضر (teacher) الدخول: `authenticate` في `user_service.py` يتحقق، يخزن session، ولو كان رئيس قسم أيضاً يحسب أعلى دور إلى `redirect` يقصده `landing_endpoint` — فلو دخل كمحاضر يرى جدول محاضراته فقط، ولو دخل كرئيس قسم يرى أقسامه."

### 11) افترض أن المستخدم قام بهذا الإجراء، صف لي ما يحدث خطوة بخطوة.
اختر إجراءً من القائمة (login، إضافة مقرر، جدولة حصة، تسليم محتوى، رفع ملف، استوديو الحذف) وصفه بـ 5-7 خطوات كالآتي (لإضافة مقرر):
1. فتح الصفحة → JS يجلب المقررات.
2. ضغط "إضافة" → modal يفتح.
3. تعبئة الحقول + اختيار القسم.
4. submit → fetch POST `/api/plans/create` أو route.
5. before_request يفحص CSRF والصلاحية.
6. التحقق من التكرار → INSERT → commit.
7. `{ok:true}` → إغلاق modal وتحديث الجدول.

### 12) أين يبدأ التنفيذ؟ وأين ينتهي؟
يبدأ من **`create_app()`** في `app.py:92` عند تشغيل السيرفر، ثم بانتظار الطلبات. كل طلب يبدأ بوصول الـ HTTP وينتهي بتوليد الـ Response (HTML أو JSON). مسار صلاح كامل موصوف في §48 أعلاه.

### 13) من المسؤول عن هذه العملية: Frontend أم Backend أم Database؟ ولماذا؟
قاعدة الجواب الدائم: **العرض والتفاعل = Frontend، المنطق والصلاحيات = Backend، التخزين = Database** — والأمان طرف Backend دائماً. مثال: "فتح النافذة = Frontend (JS)، التحقق من تكرار الكود = Backend، حفظ السجل = Database."

   الجواب: هذه الدالة تُعرّف في `courses_list.js` (تبديل العروض بين جدول/محتويات)، والقالب يدعوها عند فتح طريقة العرض. لو رمز الخطأ عند التنزيل فالسبب أن الفسحة تطيب بطريقة تعددية لكن المكتب تسلسل؛ الحل: التأكد من استدعائها بعد تحميل الملف (تعريف `defer` أو تحميل آخر).

2. **تعريف `switchCodesEditorMode` مكرر/متعارض (في ملفات/أسطر متعددة):**
   الجواب: هذا **تعارض بين صورتين** — إحداهما في قاعدة صفحات (server-rendered template script tag) وأخرى في `courses_list.js`. صحيح أن على JS مفهوم "آخر تعريف يربح" هنا؛ الحل المنطقي توحيد التعريف في ملف واحد، وهذا معلوم معروف أعالجه.

3. **حالات PENDING_TEACHER / PENDING_HOD / PENDING_EXAM "ميتة" في `course_content_service.py`:**
   الجواب: هذه حالة **التخزين المؤقت** لسير العمل — قد توجد في الجزء م�ة (مثل PENDING_TEACHER مع عدم وجود مسار clear من الخطوة السابقة في التدفق الحالي). توجد دالة `get_permitted_states` تحدّ من الانتقال المسموح؛ وبعض الحالات قد تُترك للتوثق مستقبلاً أو تُعالج في الانتقالات الحقيقية (نشر مباشر). أعرض آلة الحالة الفعلية إن طُلب.

## ملحق 4: مخطّط تدفق كل طلب (تحفظه وترسمه على الورق إن طُلب)

```
المتصفح
  │  (click / submit / fetch)
  ▼
HTTP Request (GET/POST) + Cookies
  ▼
Flask `before_request`:
   1) CSRF check (security/csrf.py)  ← فقط لطلبات تغيير الحالة
   2) enforce_permissions (app.py:174) ← deny-by-default
  ▼
Route / View Function (Blueprint)
   ├─ @login_required / @permission_required / @role_required
   ├─ قراءة request (form / args / json)
   ▼
Service Layer (services/*) — منطق العمل + القواعد
  ▼
Repository / sqlite3 (database/*) — SQL parameterized + db.commit()
  ▼
Response:
   ├─ render_template(...) → HTML صفحة
   ├─ redirect(...)  → إعادة توجيه (PRG)
   └─ jsonify({ok:true|false, ...}) → للـ JavaScript
  ▼
المتصفح يعرض النتيجة
```
